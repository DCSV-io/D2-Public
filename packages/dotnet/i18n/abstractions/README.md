# DcsvIo.D2.I18n.Abstractions

The part of the i18n stack that domain layers can reference: the `TKMessage` type and the `ITranslator` interface.
The package has no external dependencies (no NuGet packages, no other shared-library references, only what the .NET
runtime ships), so a domain layer that references it does not also pick up DI containers, configuration loading or
file IO.

The `TK` constants (one `TKMessage` instance per translation key, generated by a source generator from
`contracts/messages/en-US.json`) are in the sibling `DcsvIo.D2.I18n.Keys` project, which references this one for the
`TKMessage` type. The runtime classes (`Translator`, `SupportedLocales` and the `AddD2I18n` DI extension) are in the
sibling `DcsvIo.D2.I18n` project. Domain code never references that project.

---

## Install

```bash
dotnet add package DcsvIo.D2.I18n.Abstractions
```

## Why split

`D2Result.Messages`, `InputError.Errors` and any domain factory message slot use `TKMessage`, so domain code must be
able to reach the type. By convention, domain code takes only value-typed dependencies that have no dependencies of
their own. The runtime translator needs `IConfiguration`, `IServiceCollection` and file IO. If it were in the same
project as `TKMessage`, every domain project would transitively pick up DI and Configuration just to spell an error
key. The Abstractions split prevents that.

The split follows the same pattern as `Microsoft.Extensions.Logging.Abstractions` and `Microsoft.Extensions.Logging`.

## TKMessage - the structural primitive

Every translatable string is a `TKMessage`:

```csharp
// Common case - no params:
D2Result<T>.ValidationFailed(messages: [TK.Common.Errors.NOT_FOUND]);

// Parameterized - bind via With():
D2Result<T>.ValidationFailed(
    messages: [TK.Auth.Errors.PASSWORD_WEAK.With("minLength", "12")]);

// Per-field input errors - same primitive:
D2Result<T>.ValidationFailed(
    inputErrors: [new InputError("email", [TK.Common.Validation.EMAIL_INVALID])]);
```

Key facts:

- Internal constructor. A producer can construct a `TKMessage` only through the `TK.*` constants that the source
  generator emits in the sibling `DcsvIo.D2.I18n.Keys`. The type has no public constructor, so an untranslated literal
  cannot appear in `D2Result.Messages`.
- Immutable. `With(name, value)` and `With(IReadOnlyDictionary<string, string>)` return _new_ instances and never
  change the original, so the static readonly `TK` constants never change.
- Record equality with order-independent params. Two `TKMessage` instances with the same key and the same param
  bindings compare equal, regardless of the order in which `With()` was called.
- The wire format is the code shape. The JSON shape in code and on the wire is the same, with no separate in-memory
  representation.

## Wire format

`TKMessageJsonConverter` sets the wire shape, which is also the in-code shape:

```json
// No params:
{ "key": "common_errors_NOT_FOUND" }

// With params:
{ "key": "auth_errors_PASSWORD_WEAK", "params": { "minLength": "12" } }
```

Used inside `D2Result.Messages` array:

```json
{
  "success": false,
  "statusCode": 422,
  "messages": [{ "key": "common_errors_VALIDATION_FAILED" }],
  "inputErrors": [
    {
      "field": "email",
      "errors": [{ "key": "common_validation_EMAIL_INVALID" }]
    }
  ]
}
```

The client translates. SvelteKit and Paraglide read the wire-format `TKMessage` objects and render them in the active
locale. The server does not use the locale on the HTTP response path, so a CDN can cache the responses and
`Vary: Accept-Language` does not split the cache.

The server-side `Translator` (in the runtime library) is used only for outbound notifications (email, SMS and push).
For these, the recipient's preferred locale comes from the user profile, and the rendered text must be inlined into the
notification payload before delivery.

## TK constants

The `TK.*` constants that every producer references (for example `TK.Common.Errors.NOT_FOUND`) are `TKMessage`
instances that a source generator emits. They are in the sibling `DcsvIo.D2.I18n.Keys` project, which runs the
`DcsvIo.D2.I18n.SourceGen.TKGenerator` and references this project for the `TKMessage` type. That project's README
documents the decomposition rules, the build-time diagnostics and the reason for code generation.

## ITranslator - the runtime contract (implemented in `DcsvIo.D2.I18n`)

```csharp
public interface ITranslator
{
    string T(string locale, TKMessage message);
    bool HasKey(string key);
}
```

`T()` resolves the locale with `SupportedLocales.Resolve` (canonical match, then language fallback, then base locale),
looks up the key, falls back to the base-locale translation, and then falls back to the raw key string. It never
throws on a missing key: the raw key is readable by a developer and is a debugging signal.

`HasKey` is O(1) because it uses a pre-computed `HashSet<string>` that is filled when the catalog loads.

`DcsvIo.D2.I18n.Translator` implements the interface. Domain code references it only to render text for an outbound
notification. Other domain code puts `TKMessage` instances into `D2Result`, and the boundary translates them.

## Tests

The `DcsvIo.D2.Tests` I18n unit suite covers every `TKMessage` operation, immutability, JSON round trips and
adversarial inputs, and the pure-logic paths of the source generator's emitter and decomposer. Its test classes:

- `TKMessageTests` - equality (incl. order-independent params), JSON roundtrip, malformed JSON handling, immutability
  of `With()`, integration as part of `D2Result.Messages` arrays.
- `SourceGen/KeyDecomposerTests` - happy path + every invalid edge (leading/trailing/consecutive underscores,
  identifier-starts-with-digit, unicode rejection, reserved word collision), plus property test against every real key
  in `en-US.json`.
- `SourceGen/TKEmitterTests` - single-key snapshot, multi-domain emission, alphabetical determinism (cache stability),
  all diagnostics (D2I18N001-006), 200-key smoke test.
- `SourceGen/DiagnosticIdsTests` - pins every D2I18N### identifier to its stable value, because renaming one is a
  breaking change.

`TKGeneratedTests` runs the Roslyn-host integration (`TKGenerator.Initialize`) end to end: every constant in `TK` must
round-trip back to a key in `en-US.json`.

## Out of scope

- Compile-time call-site safety: a `T(TKKey)` overload where `TKKey` is a phantom type that proves the key exists.
  The `T(TKMessage)` API already restricts construction to the `TK` constants, and the remaining safety gap is too
  small to justify the extra type-system complexity.
- Generator-emitted XML doc comments on `TK` constants: embedding the en-US text in the generated `<summary>` would
  show the message in IntelliSense, but the generator would have to check translation values for characters that are
  safe in XML doc. The added build-time complexity is not justified.
- Per-message context metadata, such as severity or audience tags. It would require extending `TKMessage` and the wire
  format, and no use case needs that wire-format change.
