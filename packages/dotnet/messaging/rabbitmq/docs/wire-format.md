# DcsvIo.D2.Messaging.RabbitMq - wire format

The bytes [`DcsvIo.D2.Messaging.RabbitMq`](../README.md) puts on the wire: the envelope, its fields, and the AMQP
header contract a consumer of another runtime has to honor.

## Envelope

There is no envelope wrapper. The wire body is one of:

- Plaintext path: the raw `System.Text.Json` serialization of the message
  value (UTF-8 bytes).
- Encrypted path: a single AES-256-GCM frame produced by
  `DcsvIo.D2.Encryption.IPayloadCrypto.Encrypt`:
  ```text
  [version=1 byte][kid_len=1 byte][kid:UTF-8 bytes][nonce:12 bytes][ciphertext+tag]
  ```
  The kid is also copied into the `x-d2-encryption-kid` AMQP header, so an operator
  triaging the DLQ can decide whether archive keys are needed without first
  decrypting. The binary frame-layout byte offsets are defined by a spec and generated by
  `DcsvIo.D2.Encryption.Frame.SourceGen`.

`EncryptedBodyComposer` chooses the path from the descriptor's `Encryption`
field. Plaintext on a domain that should be encrypted - or vice versa - is a
spec edit, not a code edit; the resolver reads the new descriptor after the
next build.

## Sealed (asymmetric) mode

A domain declares its encryption mode in `contracts/encryption-domains`
(`mode: symmetric | sealed`, default `symmetric`). On a sealed domain, such
as a host's `orders` domain, every service seals a payload to the consumer
service's public key (version-2 ECDH-ES frame), and only that one consumer
opens it. The mode and the consumer are each defined once, in the domain's catalog entry, and are read from the
generated catalog through `MqMessageDescriptor.IsSealed` and `.ConsumerService`.
No second generated surface exists.

`EncryptedBodyComposer` has a sealed branch. On publish it resolves the keyed
`IPayloadSealer` by consumer service and produces a v2 frame; on consume it
resolves the keyed `IPayloadOpener` by the same key. A producer host that never
registered a sealer, or a consumer host with no opener, lacks the keyed
registration, so `GetRequiredKeyedService` throws. The publish then fails, and the consume path
sends the message to the DLQ; the message is never sent as plaintext and never dropped silently.
Two sealed domains that share a consumer share one sealer/opener.

`SealedConsumerStartupCheck` (registered unconditionally by
`AddD2MessagingRabbitMq`, never by the sealing call) fails host startup - before
any consumer channel opens - when a subscriber consumes a sealed domain but no
matching `IPayloadOpener` is registered, so a forgotten sealed-opener registration
fails at startup and does not send every delivery to the DLQ. Sealed sealer/opener material is
host-supplied through the public encryption seams (`IPayloadSealer` / `IPayloadOpener`
keyed DI + provenance marks such as `EncryptionKeyringSource.Managed` for
managed sources). This shared package uses whichever keyed sealer and opener the host
registered, and depends only on other shared packages. The TypeScript twin
(`@dcsv-io/d2-messaging-rabbitmq`) enforces the same constraint through its types.

## Design rationale: JSON rather than binary protobuf

- Any language with a JSON parser can read a decrypted body without
  `protoc`-generated code, so consumers can be written in any language.
- A DLQ message decrypts to a UTF-8 JSON document, which can be searched with `grep`, compared with
  `diff` and replayed.
- The size and parse cost are bounded at the message rates this
  system runs at.

## AMQP header contract

Every published message carries the headers below. Headers stay plaintext in
the broker - they MUST NOT carry user identity, scopes, fingerprints, or any
other sensitive context.

| Header                | Direction            | Purpose                                                                                                                                                                                                                                                                                      |
| --------------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `content-type`        | producer -> consumer | Always `application/octet-stream`. Body is an opaque byte sequence (encrypted or JSON).                                                                                                                                                                                                      |
| `x-proto-type`        | producer -> consumer | The CLR fully qualified name (FQN) of the message type, so a reader can inspect the type without parsing the body.                                                                                                                                                                           |
| `message-id`          | producer -> consumer | UUIDv7 (sortable, includes timestamp). Stable across publish retries: the publisher generates it once per `PublishAsync` call, so a retry of a publish that the broker received but did not confirm does not bypass the consumer's idempotency window.                                       |
| `timestamp`           | producer -> consumer | ISO 8601 UTC at publish time.                                                                                                                                                                                                                                                                |
| `traceparent`         | producer -> consumer | Full W3C trace-context string `00-{traceId}-{spanId}-{flags}`. The consumer parses it via `ActivityContext.TryParse` and starts a `Consumer`-kind span whose parent is the publish span - cross-hop trace assembly works in any OTel backend.                                                |
| `tracestate`          | producer -> consumer | Optional W3C vendor-specific trace state, forwarded as-is.                                                                                                                                                                                                                                   |
| `x-d2-encryption-kid` | producer -> consumer | Encryption key id. Set only on encrypted messages.                                                                                                                                                                                                                                           |
| `x-d2-context`        | producer -> consumer | Base64url-of-JSON encoded `PropagatedContext` - request id, request path, fingerprints, WhoIs hash. It carries no identity (UserId / OrgId / Scopes), which is rebuilt from the JWT at every hop.                                                                                            |
| `x-d2-failure-reason` | DLQ-only             | JSON-encoded `DlqFailureMetadata`, every field: `cause`, `errorCode`, `detail`, `attemptCount`, `traceId`, `nackedBy`. Attached by the consumer when republishing to the queue's DLX - see [DLQ republish-with-failure-header](publisher-and-consumer.md#dlq-republish-with-failure-header). |

> The catalog of each header's direction and purpose is in this
> document, which is the operational reference. The wire-value constants
> (for example `AmqpHeaders.MESSAGE_ID = "message-id"`) are generated into
> `DcsvIo.D2.Headers.Amqp` from
> `contracts/headers/headers.spec.json`.
