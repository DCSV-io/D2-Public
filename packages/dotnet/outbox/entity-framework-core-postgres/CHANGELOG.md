## 0.2.0 - 2026-08-22

### API-breaking

- `OutboxRelay<TDbContext>` is removed. `OutboxRelay<TDb>` replaces it, generic
  over the database's application-layer context interface. The relay never used
  `TDbContext` at runtime; it resolved its store from the System-plane work scope
  and still does.
- The `OutboxRelay` constructor no longer takes a leading `string outboxName`. It
  takes `IEnumerable<IOutboxDispatcherBinding<TDb>>` in place of
  `IEnumerable<IOutboxDispatcher>`, `IOptionsMonitor<OutboxOptionsFor<TDb>>` in
  place of `IOptionsMonitor<OutboxOptions>`, and one new argument,
  `IServiceProviderIsService`, which it uses once to refuse a relay whose database
  has no registered store.
- `AddD2OutboxRelayPostgres<TDbContext>(string outboxName)` is removed.
  `AddD2OutboxRelayPostgres<TDb>()` replaces it, and its whole body is one
  `AddHostedService<OutboxRelay<TDb>>` call.
- The private keyed relay-registration marker added in 0.1.1 is gone, along with
  the registration scan that read it. `AddHostedService` deduplicates on the
  implementation type, which is now one closed type per context interface, so there
  is one relay per interface by construction. Two calls for one interface still
  register one relay; two interfaces still register two.
- The registration-time store-pairing check is gone. The property it checked still holds: a relay
  registered for a database with no `IOutboxStore<TDb>` still fails host start,
  now from the relay's own constructor, which is the same moment the hosted
  services are resolved. The other composition it used to refuse - two outboxes
  over one context, with a store under only one of them - is refused earlier now,
  by `AddD2OutboxEntityFrameworkCore<TDb, TDbContext>`, which records the
  interface-context pair in both directions. Together, one store per interface, one
  interface per context type, and a relay that cannot start without its store give
  one relay per registered context type. Which physical table that context maps
  is outside what registration can see and stays the host's.

### Changed

- The `Microsoft.EntityFrameworkCore` package reference is dropped. It was
  declared for the `DbContext` the relay was generic over, and the relay no longer
  refers to a `DbContext`.

## 0.1.1 - 2026-08-22

### Fixed

- `AddD2OutboxRelayPostgres<TDbContext>` registers one relay per context-and-name
  pair.
  The call went through `AddHostedService`, which deduplicates on the
  implementation type, and every name over one context type builds the same
  closed `OutboxRelay<TDbContext>`. Two names over one context therefore left
  one relay running: it indexed the first name's dispatchers only, and every
  message staged under the second name recorded `NO_DISPATCHER_MARKER` until it
  was abandoned. The name now travels with the registration on a private keyed
  marker, and the hosted-service descriptor is added directly. Two calls under
  one name still register one relay, and the store-pairing check still runs per
  registration. The fix is registration-level: two names over one context type
  still read one table, whose rows carry no name column, so each relay can
  claim rows staged under the other name and record `NO_DISPATCHER_MARKER` on
  them before the right relay reaches them. A host pairs one name with one
  context type until the storage half distinguishes names.

## 0.1.0

### Added

- Initial PostgreSQL leaf of the transactional outbox.
- `OutboxRelay<TDbContext>`: the hosted service that claims a batch of due
  messages under a PostgreSQL try-advisory-lock, hands each to the dispatcher
  whose kind matches, and records the outcome. Moved here from
  `DcsvIo.D2.Outbox.EntityFrameworkCore` unchanged, along with
  `NO_DISPATCHER_MARKER` and `DISPATCHER_THREW_MARKER`. The advisory lock is the
  provider binding, and it was reaching every consumer of the storage package -
  including service layers whose reference rules forbid a database driver - while
  the row and the staging seam need no provider at all.
- `AddD2OutboxRelayPostgres<TDbContext>` on `IServiceCollection`: registers the
  relay under one outbox name. `AddD2OutboxEntityFrameworkCore<TDbContext>`
  registered the store, the staging seam and the relay together; it keeps the
  store-side registrations, and a host that delivers its staged messages adds
  this call beside it under the same name. A host that makes this call under a
  name no store is registered under fails to start, rather than running a relay
  that claims nothing.
